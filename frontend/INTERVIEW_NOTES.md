## 1. 项目一句话介绍（背下来）

> 「默语共鸣」是一个面向听障儿童的无障碍沟通与学习 App。我负责 **Flutter 前端**，后端和算法由同事负责。前端核心是：把用户的语音或文字，经算法改写成手语语序，用一张张"词卡"实时渲染出来。

## 2. 业务背景与我的职责

### 这个 App 干什么
面向听障儿童，四个板块：
- **沟通**：语音/文字 → 手语语序词卡（核心功能）
- **阅读**：读物跟读，原文对照手语
- **练习**：拼图、田字格、跟读三种题型
- **我的**：用户信息、成长进度

### 我负责哪块（面试官爱问"你做了什么"）
我**只负责 `frontend/` 这个 Flutter 工程**：页面与交互、路由导航、状态管理、网络层封装、Token 本地存储、SSE 事件消费与渲染、前端错误处理。
后端接口和算法推理是同事做的，我们通过约定的 API / SSE 契约联调。

> 诚实加分点：多人协作的项目，讲清边界比夸大贡献更让人信服。

## 3. 技术栈（版本填真实值）

开发环境实际用的：**Flutter 3.44.6 / Dart 3.12.2**（pubspec 里的最低约束是 3.22 / 3.4，被追问可以这么区分着说）。

| 库 | 干什么 | 为什么用它（理解，不是我选的） |
|---|---|---|
| flutter_riverpod | 状态管理 | 比 setState 更适合中大型项目，全局状态和异步状态管理更清晰 |
| go_router | 路由 | 声明式路由，方便做登录守卫、底部导航（ShellRoute）、深层跳转，比手写 Navigator 好维护 |
| dio | 网络 | 方便统一处理 baseUrl、请求头、拦截器、错误和 401 处理 |
| shared_preferences | 本地存储 | 存 Token 和基础配置，实现简单，用来做登录态恢复 |
| record / just_audio | 录音 / 播放 | 沟通页录音、TTS 播放 |
| rive / flutter_svg | 动画 / 矢量图 | 承载吉祥物"呦呦"动画和插画资源 |

被追问"为什么 Riverpod 不用 Bloc / Provider"的稳妥回答：
> Riverpod 可以看成 Provider 的改进版，解决了 Provider 依赖 context、容易类型报错的问题；比 Bloc 更轻、样板代码少。项目定了 Riverpod，我理解是想在轻量和可维护之间取平衡。

## 4. 架构怎么讲

### 目录结构（一句话说清分层）
```text
lib/
├── core/        # 全局基建：路由、网络、主题、存储、工具
├── features/    # 按业务拆模块：auth / chat / reading / practice / profile
├── shared/      # 跨模块复用：通用组件、通用模型
└── main.dart    # 入口
```
讲法：
> 按"基建 / 业务 / 复用"三层分。core 放谁都要用的底座，features 按业务模块各管各的，shared 放跨模块共享的组件。这样模块之间不乱依赖，好维护。

### 页面结构（三层，好记）
> 整个 App 就三层：**门口**（启动/登录/注册，无底部导航）→ **主屋**（底部 4 tab：沟通/阅读/练习/我的）→ **里间**（从 tab 点进去的详情页，比如点一本书进阅读页，全屏盖住导航）。

## 5. 已实现模块沉淀

> 每完成一个模块，按"一句话亮点 / 可复述版 / STAR / 可追问 / 回答提纲"补一条。

### 模块：工程骨架 + 网络与路由基建【已实现】

- **一句话亮点**：搭了分层清晰的前端骨架，网络层用 Dio 拦截器统一处理请求追踪、鉴权、错误码映射和 401 登出。

- **可复述版（口语化）**：
  > 我在 Dio 上加了拦截器统一管网络这层。每个请求自动带一个 X-Request-ID 方便追踪；非公开接口自动带上 Token；后端返回错误时，统一把错误码转成前端的异常类型；如果是 401（登录失效），就自动清 Token、把用户踢回登录页。这样各个页面就不用各自处理这些通用逻辑了。

- **STAR**：
  - S：多页面 App，网络请求多，鉴权、错误处理如果每个页面各写一套会很乱。
  - T：把网络层的通用逻辑统一收口。
  - A：用 Dio 拦截器做了三件事——注入请求追踪 ID、自动带 Token、统一错误码映射 + 401 全局登出。
  - R：页面只管发请求，不用重复写鉴权和错误处理；登录态失效能全局兜住。

- **可追问点**：
  1. Dio 拦截器的执行顺序？（onRequest 正序、onResponse/onError 逆序）
  2. 401 怎么做到"全局"跳登录？（拦截器里拿到 401 → 调 authProvider 强制登出 → go_router 的 redirect 监听登录态变化自动跳登录页）
  3. 为什么要 X-Request-ID？（前后端排查问题时能对上同一条请求的日志）

- **回答提纲**：拦截器统一收口 → 三个职责（追踪/鉴权/错误）→ 401 联动路由守卫。

### 模块：登录态与路由守卫【已实现】

- **一句话亮点**：用 go_router 的 redirect 实现登录守卫，启动读 Token 决定去登录页还是主页，登录态一变路由自动跳转。

- **可复述版**：
  > App 启动先进闪屏页，去读本地存的 Token。没登录，你想进任何主页面都会被拦回登录页；已经登录了，你想回登录页会被弹进主页。这个是 go_router 的 redirect 统一做的，不是每个页面各自判断。登录态用 Riverpod 管，状态一变，路由用一个 refreshListenable 监听到就自动重新判断该去哪。

- **可追问点**：
  1. redirect 什么时候触发？（每次路由变化都会走一遍）
  2. 登录成功后怎么自动跳？（Riverpod 状态变 → 通知 go_router 刷新 → redirect 重新计算）
  3. ShellRoute 是干嘛的？（给底部 4 tab 做共享外壳，切 tab 时外壳不重建）

### 模块：资产管理【已实现】
- **一句话**：Flutter 资产是 pubspec 声明式注册的；踩过"声明了空目录导致构建失败"的坑，用占位文件解决。
- **可追问**：flutter_gen 是什么？（根据资产生成强类型引用，避免手写路径字符串出错）

## 6. 规划中模块（只讲设计，别讲成做完了）

### SSE 流式渲染【规划中】
- **设计思路**：沟通页发请求后，后端用 SSE（Server-Sent Events）分阶段推事件——先回显原文、再分词、再精炼语序。前端用 Dio 的 stream 模式逐行解析 event/data，每来一个事件就更新词卡状态，实现"边算边显示"。
- **可追问**：SSE vs WebSocket？（SSE 单向、服务器推��户端、基于 HTTP、自动重连，适合这种流式下发；WebSocket 双向、更重。这里只需服务器单向推，SSE 够用且简单。）

### Mock 数据驱动【规划中】
- **设计思路**：后端没好之前，前端先用本地假数据把页面喂活，能独立演示。Mock 层和真实接口层分离，将来接真接口只换数据来源。这本身是个好的面试故事："我怎么在后端未就绪时保持前端可持续开发和演示"。

## 7. 通用八股（按项目相关度，随开发补）

- **Flutter 三棵树**：Widget（配置）/ Element（桥梁）/ RenderObject（绘制）
- **StatelessWidget vs StatefulWidget**：有无内部可变状态
- **Future vs Stream**：单个异步结果 vs 多个异步事件流（SSE 用 Stream）
- **async / await / async***：async* 配合 yield 产生 Stream
- **状态管理演进**：setState → InheritedWidget → Provider → Riverpod
- **go_router vs Navigator**：声明式 vs 命令式
- **热重载 vs 热重启**：hot reload 保状态改 UI，hot restart 重置状态

> 每个八股回答时都尽量"带一句本项目的例子"，比问答本身更打动人。
