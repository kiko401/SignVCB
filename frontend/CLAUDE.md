## 项目职责边界

### 前端负责
- 页面渲染
- 用户交互
- 路由与导航
- 状态管理
- Token 本地存储
- API 调用
- SSE 事件接收、解析与渲染
- 加载态 / 空状态 / 错误态
- 动画与视觉资源加载
- 根据配置控制前端显示逻辑

### 前端不负责
- 后端业务逻辑
- 数据库设计
- 鉴权策略本身
- SSE 业务语义定义
- 算法推理与计算逻辑
- 算法服务实现
- 服务间调用逻辑

如果某个功能依赖后端或算法端，但文档或代码未明确：
- 不要自行假设为“已经存在”
- 不要伪造接口语义
- 应明确标记为“待确认”或“前端临时 Mock 适配”

### 协作现实（重要背景）

- 后端和算法端由**用户的同事**负责，用户**只做 `frontend/` 这一个 Flutter 前端项目**。
- **同事比用户先开工**，联调契约由她定。因此契约相关的不确定项，默认策略是"等她的实际代码 / 契约文档"，而不是替她做决定或照前端设计文档去猜。
- 联调返工成本最小的做法：**先推进不依赖契约的纯前端部分**（设计系统、通用组件、页面静态骨架、路由导航），把 data/service 层与真实契约的对接留到契约确定后再补。

## 重要认知：文档分层与契约权威性

### 文档分层

| 文档 | 作用 | 权威性 |
|------|------|--------|
| `../docs/api_contracts.md`、`../docs/data_contracts.md` | 三端联调契约：API 路径、请求/响应字段、数据模型、SSE 事件 | **联调契约最高权威** |
| `docs/前端详细设计文档.md` | 前端视觉、组件参数、页面职责、结构规范、交互动效 | 前端设计权威（仅设计层） |
| `TODO.md` | 当前实施阶段、任务顺序、下一步执行列表 | 当前实施态 |
| `INTERVIEW_NOTES.md` | 面试表达、项目亮点、可追问点、八股整理 | 复盘与表达材料 |
| 当前代码 `lib/` | 当前真实实现状态 | 当前事实 |

**不要把设计文档中的目标能力误判为已经实现。**  
**代码现状优先代表现实，设计文档优先代表目标。**

### 契约权威性（关键，务必遵守）

后端和算法端由用户的同事负责，**联调契约也由她定，且她比用户开工早**。因此：

- **联调契约层**（API 路径、请求/响应字段名与类型、数据模型如 AlignmentOp、SSE 事件名与字段）：以**同事的实际后端/算法代码**或根目录 `../docs/api_contracts.md`、`../docs/data_contracts.md` 为准。
- **前端设计层**（配色、字号、圆角阴影、组件参数、页面布局、交互动效、呦呦动画）：以 `docs/前端详细设计文档.md` 为准。
- ⚠️ **已知冲突**：`docs/前端详细设计文档.md` 与真实契约存在不一致（例如 API 路径可能缺 `chat` 段、AlignmentOp Dart 类缺 `source` 字段）。**遇到契约相关内容，一律以契约文档 / 同事实际代码为准，不以前端设计文档为准。**
- 若某契约细节在契约文档和同事代码中都无法确认：**标记为"待确认（等同事实现）"，不自行假设**。可先推进不依赖契约的纯前端部分（设计系统、通用组件、页面静态布局），把 data/service 层留到契约确定后再接。

## 长期工作原则（每次会话都要遵守）

### 1. 先做最小 MVP，不追求一口气做完整 App
- 设计文档是目标态
- 当前开发以“逐步闭环”为主
- 优先完成能运行、能验证、能演示的最小链路

### 2. 核心链路优先，边缘功能后置
优先顺序默认是：
1. 工程可运行
2. 编译通过
3. 登录闭环
4. 主框架与路由
5. 聊天核心链路
6. SSE 稳定性
7. 阅读与练习页面
8. 动画与资源细节
9. 优化与测试补齐

### 3. 改动聚焦，不要无关扩散
- 核心链路修复、局部 bug：优先最小 diff
- 新增页面、占位模块、新文件：可适度追求清晰结构
- 不要为了“显得完整”顺手扩展无关功能

### 4. 每次迭代都必须验证
改完必须验证，不能只写代码不测。  
优先提供最小可执行验证方案。

### 5. 不确定就直说
- 不要编造接口、状态、后端能力、算法语义
- 无法从文档或代码确认的内容，明确标记为“待确认”

### 6. 完成即更新文档
每完成一个独立模块或阶段后，及时更新：
- `TODO.md`
- `INTERVIEW_NOTES.md`

如果任务状态变化、优先级变化、阶段目标变化，更新 `TODO.md`。  
如果本次开发形成了新的项目亮点、难点、常见问法、面试表达，更新 `INTERVIEW_NOTES.md`。

### 7. 统一 UTF-8 编码
- 所有文档必须使用 UTF-8
- 不允许乱码
- 如果发现编码异常，优先修复编码问题再继续

### 8. 给学习型反馈
不只是做项目，也要帮助用户理解。  
完成后默认补充：
- 本次最该学会的内容
- 哪些点先不用深挖
- 怎么测试
- 如果失败优先查哪里

### 9. 控制 token 消耗
- 输出优先结论、计划、文件列表、验证结果
- 避免无意义长篇空话
- 但遇到用户明确要学习 / 面试总结时，必须给足够有用的信息

## 工程实现规则

### 基本规则
- 设计层（视觉/组件/布局）遵循 `docs/前端详细设计文档.md`；契约层（API/数据模型/SSE）遵循 `../docs/api_contracts.md`、`../docs/data_contracts.md` 或同事实际代码，二者冲突时以契约为准
- 不擅自更换技术栈
- 不新增依赖，除非先说明原因、收益和代价
- 不重写整个项目
- 优先保持最小 diff
- 不修改与当前任务无关的代码
- 不顺手修复无关问题
- 不删除现有功能，除非明确说明原因
- 不在代码中写密钥、密码、Token 或敏感配置

### 结构规则
- `core/`：全局基础设施（路由、网络、主题、存储、工具）
- `features/`：按业务拆分模块
- `shared/`：跨模块复用组件
- `assets/`：资源文件
- `test/`：测试文件

### 设计规则
- 页面负责展示与交互
- 状态放在 provider / notifier 中统一管理
- 网络请求通过 API / service 层处理
- 数据模型统一定义，不在页面里临时拼 JSON
- 重要业务状态要清晰、可追踪、可验证
- 要考虑加载中、成功、失败、空数据、超时、重试

## Git 提交规范

格式：`<type>(<scope>): <subject>`（主题用中文）

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（不含功能变更） |
| `style` | 代码格式、注释（不影响逻辑） |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 构建脚本、依赖、配置等 |

示例：`feat(chat): 实现 SSE 事件分发器与词卡状态机`

分支命名：
- 功能分支：`feature/<module>-<feature>`（如 `feature/chat-sse`）
- 修复分支：`fix/<bug-description>`
- 主分支 `main` 受保护，仅通过 PR 合入

## 本地开发与联调实操

### 常用命令（在 `frontend/` 目录下执行）
- 拉取依赖：`flutter pub get`
- 静态检查：`flutter analyze`
- 跑测试：`flutter test`
- 生成资产代码：`dart run build_runner build --delete-conflicting-outputs`（改动资产目录后）
- 运行（注入后端地址）：`flutter run --dart-define=BASE_URL=http://<后端地址>:8081`

### 后端地址（BASE_URL）
- 代码里通过 `--dart-define=BASE_URL=...` 注入（见 `lib/core/network/dio_client.dart`），默认 `http://127.0.0.1:8081`。
- **Android 模拟器**连本机后端：用 `http://10.0.2.2:8081`（模拟器里 `10.0.2.2` 指向宿主机，`127.0.0.1` 指向模拟器自己）。
- **真机**连本机后端：用宿主机局域网 IP，如 `http://192.168.x.x:8081`，且手机与电脑同一局域网。
- iOS 模拟器：可直接用 `127.0.0.1`。

### 注意事项
- 不要泄露真实密钥；不要把敏感配置写进代码或文档。
- 如果存在 `.env` / 本地配置，仅引用，不输出真实值。
- 如果启动或测试失败，优先明确失败原因，而不是假设已经成功。
